# Bounce tracking: a per-SprintEntry count of QA send-backs, with team-level metrics

The team's flow is Dev finishes → QA tests → if QA finds a bug the ticket goes back to the developer, repeating until QA passes it, which is what makes it `Done`. Until now the app could not see that loop: a ticket that bounced four times looked the same as one that passed first time. A **bounce** is one trip from QA back to the developer after QA found a bug.

## What it records

`sprint_entry.bounce_count` — a nullable integer on each `SprintEntry`, edited on `/admin/sprint-entries` (+/− buttons) through `PATCH /sprint-entries/{id}/bounce-count` with an absolute value.

- **A count, not an event log.** It answers the questions asked (which tickets are stuck, which ticket sizes bounce most, how much of a sprint got sent back) without making someone type a row per bounce. A log (dates, causes, time-in-QA) can be migrated to later if a count turns out not to be enough.
- **Per sprint, so it restarts at 0 when a ticket is carried over.** This follows [ADR-0001](0001-ticket-sprintentry-split.md): each sprint's entry is that sprint's snapshot. Copying the count forward would count the same bounce in two sprints' metrics. The ticket's history is not lost — the *lifetime* total is the sum over its entries (by `ticket_id`, not by following `carried_from`, so a forgotten carry-over link doesn't hide history), excluding `Cancelled` entries.
- **`NULL` means "not tracked", `0` means "tracked, never bounced".** Every entry that existed before this feature is `NULL` in a closed sprint (locked history, never backfilled) and `0` in a sprint that was `Open` at migration time, so the current sprint is tracked from the start. New entries are created at `0`; the API never accepts `NULL`. Every bounce metric counts only tracked entries, so old sprints show "Not tracked" instead of a false "0 bounces".
- **A separate PATCH, not a field on the full-entry PUT.** `PUT /sprint-entries/{id}` replaces the whole entry; a client that omitted `bounceCount` would decode as 0 and silently wipe the count. The PATCH sets an absolute value (idempotent, no increment race) and reuses the closed-sprint lock (see [Close Sprint](../../CONTEXT.md#close-sprint)): a `Closed` sprint's entries reject it with 409, and reopening per [ADR-0009](0009-sprint-reopening-is-an-escape-hatch.md) lifts it. The service checks first, for a clear error, but the repository's `UPDATE` is itself conditional on the sprint being `Open`, so a sprint closing between the check and the write cannot let a change through. (The full-entry `PUT` keeps its pre-existing check-then-write window; it was not changed.)

`Done` already means "passed QA", so Velocity, Planning Accuracy and Late-Add Rate are unchanged. No "In QA" status was added: a `NotDone` entry with bounces is visibly in the loop; one with none could be either, and adding a status would touch every status-filtered metric and the lock rules.

## What it shows

- **Sprint Entries page** — the editable count per row, plus `(N earlier)` from the ticket's entries in earlier sprints (computed client-side from the full entry list the page already holds, using sprint ID order like every dashboard query here).
- **Dashboard → Stuck tickets** — `GET /dashboard/stuck-tickets`: `NotDone` entries in `Open` sprints, `Active` projects only (a live signal, like Sprint Health) whose lifetime bounces ≥ `StuckBounceThreshold` (2; the response carries the threshold as `minBounces` so the UI never hard-codes it). A carried-over ticket with 2 earlier bounces is stuck from day one of the new sprint. `Done` tickets are not listed — they are no longer stuck. **The threshold of 2 is a placeholder**, like the Sprint Health cutoffs in [ADR-0010](0010-project-sprint-health.md); with under ~6 tracked sprints any stricter cutoff would flag almost nothing.
- **Retrospective** (closed sprints, every project, per [ADR-0012](0012-sprint-retrospective-report.md)) — per sprint: total bounces, average per ticket, and tickets-that-bounced-at-least-once as a *count* (`4 of 10`). No percentage rate: with ~10 tickets a sprint, a count says more than a ratio, and every figure carries its raw numbers.
- **Bounces by ticket size** — `GET /dashboard/bounce-by-size`: fixed bands 1–2 / 3–5 / 6+ SP (by the entry's own `points_at_entry`) over *all* closed sprints with tracked data, not the retrospective's `limit` window — three sprints would leave 2–3 tickets per band. Counted per entry (consistent with ADR-0012's ticket counts), so a ticket carried over twice appears three times — which is why the API and the table call these `entries`, not tickets. The page says to read it as a hint, not a conclusion.
- **Per-developer column** — bounces ÷ the developer's tracked, non-Cancelled entries *in that one sprint*, always shown as `7 bounces / 5 tickets = 1.4`. The API returns only the raw counts; the UI derives the average, so every figure appears with its counts. The "Unassigned" row gets it too. On `/dashboard/{sprintId}` the figure covers the whole sprint and reconciles with the sprint total; on `/dashboard/{sprintId}/entries`, which already splits the sprint into current and carried-over work, it is computed per subset, so a developer there has two figures that together make up the sprint's.

## Deliberate limits

- **No per-developer ranking.** Bounce means QA found bugs in someone's work, so a developer scoreboard would reward rushing tickets to QA or hiding bugs. The per-developer figure is single-sprint, shown with raw counts, with no sorting, colour or chart by bounce, and no all-time per-developer number. A ticket row names its assignee only as context. Adding more is easy; taking it back once people see their number is not.
- **Attribution uses the ticket's current assignee**, like the existing workload columns (`ticket.assignee_id` is not snapshotted per sprint). Reassigning a ticket later moves its past bounces to the new assignee's figure. Accepted while reassignment is rare; a snapshot column on `sprint_entry` is the fix if it isn't.
- **Cancelled entries.** They are excluded from every bounce metric and the UI offers no controls on them, but `PATCH .../bounce-count` still accepts them (harmless: the value is never read). A mistaken count on an entry that was later cancelled can't be corrected in the UI, only through the API.
- **No backfill of closed sprints** (they are locked; the reopen escape hatch exists but isn't used for this) and no planning/"suggested commitment" output — that would need rework effort, which isn't recorded.

## Consequences

- When the Close Sprint auto-carry-over feature is built ([CONTEXT.md](../../CONTEXT.md#close-sprint)), it must create the carried entry with `bounce_count = 0`, not copy it.
- Retrospective bounce columns read "Not tracked" until the first sprint with tracking closes.
- `GET /dashboard/sprints/{id}` and the sprint dashboard's developer table gained `bounces` and `bounceTrackedTickets` (no precomputed average); `SprintPoints` (shared by Sprint Health and the Retrospective) gained the three raw bounce counts but Sprint Health does not use them.
